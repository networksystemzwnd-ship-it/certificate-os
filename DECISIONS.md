## Implementation decisions made while building

| ID | Date | Decision | Reason |
|---|---|---|---|
| D-101 | 2026-10-15 | API uses Go stdlib `net/http` (1.22+ routing) and `log/slog`; only third-party dependency so far is `pgx/v5` | Minimal dependency surface |
| D-102 | 2026-10-15 | Migrations: embedded plain `.sql` files (`NNNN_name.up.sql` / `.down.sql`) applied by a small in-repo runner tracking `schema_migrations` | No extra tool; inspectable status; reversible |
| D-103 | 2026-10-15 | Job queue starts as a durable Postgres table (per brain §5.1); no Redis | Brain mandate |
| D-104 | 2026-10-15 | Registration returns 409 for an existing email (reveals existence) | Usability until email verification (P1) exists; login and verification pages stay non-enumerating |
| D-105 | 2026-10-15 | Certificate Staff default permissions exclude issue/revoke/deliver/export; these are explicit per-membership grants (COS-008) | Brain §3.3: "issue certificates if permission is granted" |
| D-106 | 2026-10-15 | Validation failures use HTTP 422 with `details` map; malformed/unknown-field bodies use 400 | Brain §5.5 consistency |
| D-107 | 2026-10-15 | Sessions: opaque random token in HttpOnly SameSite=Lax cookie (`__Host-` prefix + Secure in production); only SHA-256 of token stored; absolute TTL (default 12h); status/role read live on every request | Instant suspension/revocation; DB leak yields no usable sessions |
| D-108 | 2026-10-15 | Rate limiting is in-memory per process; client IP is the TCP peer (X-Forwarded-For not trusted) | Fine for one API instance; replace with shared limiter + trusted-proxy config before scaling out or deploying behind a proxy |
| D-109 | 2026-10-15 | CSRF: required `X-CSRF-Protection: 1` header + Origin check on non-safe methods, plus strict single-origin CORS | Works with SameSite=Lax cookies and a separate web origin |
| D-110 | 2026-10-15 | Password hashing: PBKDF2-HMAC-SHA256, 600k iterations, Go stdlib (`crypto/pbkdf2`); `NeedsRehash` supports migration to argon2id later | No new dependency; revisit with `golang.org/x/crypto` |
| D-111 | 2026-10-15 | Platform roles are granted only out-of-band (`api user grant-platform-role`), never via the HTTP API | Prevent self-escalation |
| D-112 | 2026-10-15 | User-chosen infra tweaks: MinIO image `cgr.dev/chainguard/minio:latest`; API build image `golang:1.25-alpine` | Applied by product owner after local testing |
| D-113 | 2026-10-16 | Tenant resolution: the client may send `X-Institute-ID`, but it is only matched against the caller's OWN active memberships. Exactly one membership → header optional; several → header required (400 `institute_required`). Non-member and non-existent institutes return the identical 403 | Brain §6.3: tenant from membership, no enumeration |
| D-114 | 2026-10-16 | Suspended institute: members keep only `*.read` permissions (exports excluded, because they bulk-extract PII); closed institute: no member access | Brain §3.2 "explicit read-only access policy". **Confirmed by product owner 2026-10-16** |
| D-115 | 2026-10-16 | Per-membership `grants` extend role defaults but can never include owner-only (`staff.manage`, `institute.manage`) or platform permissions; enforced in code and by a DB CHECK | No escalation by grant; implements D-105 |
| D-116 | 2026-10-16 | Compile-time tenant scoping: tenant-owned repository methods take a `tenancy.Scope`, constructible only from a resolved `Tenant`. `TrustedScope` is for tests/admin tooling only; `AdminStore` is never reachable from handlers | A forgotten tenant check fails to compile rather than leaking |
| D-117 | 2026-10-16 | PostgreSQL RLS is mandatory for every tenant-owned table, enabled together with a restricted runtime role when the first such table is added (hard gate COS-RLS, blocks M3); hook `tenantdb.WithTenant` shipped; ADR-001 **Accepted** | Production-best: superuser dev DB bypasses RLS and there is nothing to protect yet |
| D-118 | 2026-10-16 | Institutes and memberships were created out-of-band (`api institute ...`, `api seed`) until application review existed. **Superseded in part by D-119/D-120**: the CLI remains for seeding, recovery and closing institutes | Onboarding workflow is a later milestone |
| D-119 | 2026-10-17 | Application lifecycle: draft → submitted → under_review → approved \| rejected \| changes_requested (→ submitted). One open application per user; the requested slug is reserved while an application is submitted/under_review/changes_requested/approved and released on rejection. Enforced by the service, the store contract and partial unique indexes | Prevents duplicate/squatted workspaces and parallel applications |
| D-120 | 2026-10-17 | Approval is one transaction: lock row, create institute + owner membership, mark approved, write audit events; any failure (e.g. slug taken, applicant suspended) changes nothing. Operations never see drafts; reviewers cannot decide their own application; a decision reason of 10–2000 characters is required for reject / request-changes and is shown to the applicant; another user's application is 404, never 403 | Integrity, conflict of interest, no enumeration |
| D-121 | 2026-10-17 | Append-only audit log: `audit_logs` has no foreign keys, DB triggers block UPDATE/DELETE, a `seq` identity column gives a stable order, metadata is sanitized (credential-like keys stripped) and holds ids/states/reasons only. API-driven changes write their event in the same transaction; CLI changes are audited as actor `cli` but NOT transactionally (the command reports an error if the audit write fails). Runtime-role REVOKE is part of COS-RLS | Tamper-evidence and traceability |
| D-122 | 2026-10-17 | Operations may suspend (reason required) and reactivate institutes (`ops.institutes.manage`); closing remains CLI-only. The audit view (`GET /api/v1/ops/audit`) is super_admin only (`ops.audit.read`). Suspended behavior is unchanged from D-114 | Least privilege; closure is effectively irreversible |
| D-123 | 2026-10-17 | MVP onboarding has no document upload: the applicant attests accuracy and authority, and operations verify offline. Email/notification of decisions is deferred (P1); applicants see status in the app. Document upload is COS-011 and needs an object-store adapter | Avoids shipping unscanned-upload risk before storage and malware-scan design exist |
| D-124 | 2026-10-21 | RLS implemented per ADR-001: `certos_runtime` NOLOGIN group role (migration 0006), login role `certos_app` created out-of-band by `api db provision-runtime-role`; API uses `DATABASE_URL` (restricted), migrations/provisioning use `MIGRATE_DATABASE_URL` (owner, required and different in production); production refuses to start if the runtime role is superuser/BYPASSRLS; runtime role has no DELETE/TRUNCATE and only INSERT/SELECT on `audit_logs` | ADR-001 production gate |
| D-125 | 2026-10-21 | Completion date and grade belong to the ENROLLMENT (student ↔ batch), not the student: one student can finish different courses on different dates with different grades. Certificates (M4) will reference an enrollment. **Awaiting product-owner confirmation.** | Data-model correctness |
| D-126 | 2026-10-21 | Course, batch and student records are archived, never hard-deleted (runtime role has no DELETE). Archiving a course with active batches, or a batch with active enrollments, is refused (409). Restore is supported. | Certificates must keep resolving their source records |
| D-127 | 2026-10-21 | Tenant-owned tables carry `institute_id`, composite `(institute_id, id)` foreign keys (a batch can only point at a course of the same institute), `ENABLE`+`FORCE` RLS with policy `institute_id = nullif(current_setting('app.institute_id', true), '')::uuid` (the `nullif` is required: the setting reverts to the empty string, not NULL, on a pooled connection). Every store call runs in `tenantdb.WithTenant`. | Fail-closed defense in depth |
| D-128 | 2026-10-21 | Audit metadata for records holds ids and changed field NAMES only, never student personal data (names, emails, phones). | Privacy; audit log is append-only and cannot be redacted |
| D-129 | 2026-10-21 | Permissions: courses and batches use `courses.read/write`; students and enrollments use `students.read/write`. Suspended institutes keep only `*.read`. | Reuses the existing capability set |
| D-130 | 2026-10-22 | Student import is CSV-only for now (UTF-8; `,` `;` or tab). XLSX needs a third-party parser (a new dependency and a new attack surface); it is deferred and the upload says how to save as CSV UTF-8. Limits: 2 MB, 2000 rows, 30 columns, 500 characters per cell (confirm runs synchronously inside the 60 s write timeout). | Dependency and safety; brain lists XLSX as P0, to be revisited |
| D-131 | 2026-10-22 | Import duplicates are never overwritten or merged: a row is skipped when its student number matches (case-insensitively, archived students included) or when name and email both match; the same email with a different name is imported with a notice (siblings share a family email). Duplicates inside the file are also skipped (first row wins). | Brain §3.4 "never silently overwrite" |
| D-132 | 2026-10-22 | Dates in an import use an explicit format chosen by the user (`iso`, `dmy`, `mdy`); day/month order is never guessed, two-digit years are rejected. | Avoid silently swapped dates on certificates |
| D-133 | 2026-10-22 | Import rows are saved one at a time through the records service (own validation, uniqueness and audit event per student, all tagged with the confirm request id); progress is stored every 100 rows and an interrupted confirm resumes after 5 minutes. A crash can lose at most the last 100 rows of progress; rows without student number or email in that window could be imported twice on resume. Audit metadata for imports holds counts only. | Reuses every records rule; bounded chunks per brain §3.4 |
| D-134 | 2026-10-22 | Uploaded rows are discarded when an import completes or is cancelled, except rows that need attention (kept for the error report). A scheduled purge of abandoned uploads is still to be built with the worker. | Data minimisation |
| D-135 | 2026-10-22 | `students.import` stays an admin/owner capability (staff can be granted it per membership); staff keep manual add/edit. Error-report cells that start with `= + - @` are prefixed with an apostrophe to block CSV formula injection. | Bulk writes are higher risk; spreadsheet safety |
| D-136 | 2026-10-22 | Go tests run with `-p 1` (CI and `make test`): the Postgres-backed packages share one test database and truncate it. | Prevent cross-package interference |
| D-137 | 2026-10-23 | `institute_invitations` is a GLOBAL (non-RLS) table: accepting happens before the invitee has any tenant context. Safety comes from the token hash lookup, the email match, and the store never exposing it through tenant routes (listing is filtered by institute id in SQL and the contract test checks isolation). Listed in `globalTables` with this reason. | RLS cannot express "the invitee may read exactly the row their token hashes to" without a tenant |
| D-138 | 2026-10-23 | Staff are invited by a one-time link the owner hands over (`/accept-invite#token=...`); no email is sent until the notification worker exists (M5). Token is 32 random bytes, only its SHA-256 hash is stored, shown once in the create response, valid 7 days, carried in the URL fragment (never sent to servers or logs) and moved to sessionStorage for the login detour. | Safe without an email provider; the link must be treated like a password |
| D-139 | 2026-10-23 | Accepting requires the signed-in account's email to equal the invited email (case-insensitive) and the institute to be active. Every failure is one identical 404 (`ErrInvalidInvitation`); a wrong account does not burn the token. Rate limited 10/15 min per user and 30/15 min per IP. | No oracle for guessing tokens or emails; a forwarded link is useless to others |
| D-140 | 2026-10-23 | Only owners manage staff (`staff.manage`). Invitable roles are admin and staff, never owner; admins cannot carry grants; staff grants limited to the validated list. Owners and your own membership cannot be changed or removed (409). Max 50 pending invitations per institute, one live pending per email (expired ones are replaced). A removed member who accepts a new invitation is reactivated. Removal is soft. | Prevent privilege escalation and lock-out |
| D-141 | 2026-10-24 | A certificate template is a PRESET (classic, modern, minimal) plus fixed fields (orientation, accent colour, title, text with a closed list of `{{placeholders}}`, signatory, footer, show/hide switches). No free-form HTML, CSS or script from users; the colour is a validated `#rrggbb`; the text must include `{{student_name}}`. | Meets D-008 and the "no arbitrary code in templates" rule |
| D-142 | 2026-10-24 | Template versions are ALWAYS immutable (not only after first use): editing saves a new version, the database allows only INSERT/SELECT on versions (runtime role) and a trigger blocks UPDATE/DELETE even for the owner. Max 100 versions per template; templates are archived, never deleted. | An issued certificate must stay reproducible; simplest rule that cannot be bypassed |
| D-143 | 2026-10-24 | Previews are rendered by the server from SAMPLE data only (never real students), as self-contained escaped HTML with a CSP, and shown in a fully sandboxed iframe. No images yet (logo/signature need file uploads, COS-011); the QR is a placeholder until issuance generates the real one. | Safe preview before any renderer or storage exists |
| D-144 | 2026-10-24 | `templates.write` is admin/owner only; staff can read and preview. A suspended institute can still read and preview, not change templates. | Consistent with D-114 and the role matrix |
