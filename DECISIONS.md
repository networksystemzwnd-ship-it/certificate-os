| D-118 | 2026-10-16 | Institutes and memberships were created out-of-band (`api institute ...`, `api seed`) until application review existed. **Superseded in part by D-119/D-120**: the CLI remains for seeding, recovery and closing institutes | Onboarding workflow is a later milestone |
| D-119 | 2026-10-17 | Application lifecycle: draft → submitted → under_review → approved \| rejected \| changes_requested (→ submitted). | D-121 | 2026-10-17 | Append-only audit log: `audit_logs` has no foreign keys, DB triggers block UPDATE/DELETE, a `seq` identity column gives a stable order, metadata is sanitized (credential-like keys stripped) and holds ids/states/reasons only. Runtime-role REVOKE is part of COS-RLS | Tamper-evidence and traceability |
| D-122 | 2026-10-17 | Operations may suspend (reason required) and reactivate institutes (`ops.institutes.manage`); closing remains CLI-only. | D-123 | 2026-10-17 | MVP onboarding has no document upload: the applicant attests accuracy and authority, and operations verify offline. | D-124 | 2026-10-21 | RLS implemented per ADR-001: `certos_runtime` NOLOGIN group role (migration 0006), login role `certos_app` created out-of-band by `api db provision-runtime-role`; API uses `DATABASE_URL` (restricted), migrations/provisioning use `MIGRATE_DATABASE_URL` (owner, required and different in production); production refuses to start if the runtime role is superuser/BYPASSRLS; runtime role has no DELETE/TRUNCATE and only INSERT/SELECT on `audit_logs` | ADR-001 production gate |
| D-125 | 2026-10-21 | Completion date and grade belong to the ENROLLMENT (student ↔ batch), not the student: one student can finish different courses on different dates with different grades. | D-126 | 2026-10-21 | Course, batch and student records are archived, never hard-deleted (runtime role has no DELETE). Archiving a course with active batches, or a batch with active enrollments, is refused (409). Restore is supported. | Certificates must keep resolving their source records |
| D-127 | 2026-10-21 | Tenant-owned tables carry `institute_id`, composite `(institute_id, id)` foreign keys (a batch can only point at a course of the same institute), `ENABLE`+`FORCE` RLS with policy `institute_id = nullif(current_setting('app.institute_id', true), '')::uuid` (the `nullif` is required: the setting reverts to the empty string, not NULL, on a pooled connection). Every store call runs in `tenantdb.WithTenant`. | Fail-closed defense in depth |
| D-128 | 2026-10-21 | Audit metadata for records holds ids and changed field NAMES only, never student personal data (names, emails, phones). | Privacy; audit log is append-only and cannot be redacted |
| D-129 | 2026-10-21 | Permissions: courses and batches use `courses.read/write`; students and enrollments use `students.read/write`. Suspended institutes keep only `*.read`. | Reuses the existing capability set |
| D-130 | 2026-10-22 | Student import is CSV-only for now (UTF-8; `,` `;` or tab). XLSX needs a third-party parser (a new dependency and a new attack surface); it is deferred and the upload says how to save as CSV UTF-8. Limits: 2 MB, 2000 rows, 30 columns, 500 characters per cell (confirm runs synchronously inside the 60 s write timeout). | Dependency and safety; brain lists XLSX as P0, to be revisited |
| D-131 | 2026-10-22 | Import duplicates are never overwritten or merged: a row is skipped when its student number matches (case-insensitively, archived students included) or when name and email both match; the same email with a different name is imported with a notice (siblings share a family email). Duplicates inside the file are also skipped (first row wins). | Brain §3.4 "never silently overwrite" |
| D-132 | 2026-10-22 | Dates in an import use an explicit format chosen by the user (`iso`, `dmy`, `mdy`); day/month order is never guessed, two-digit years are rejected. | Avoid silently swapped dates on certificates |
| D-133 | 2026-10-22 | Import rows are saved one at a time through the records service (own validation, uniqueness and audit event per student, all tagged with the confirm request id); progress is stored every 100 rows and an interrupted confirm resumes after 5 minutes. A crash can lose at most the last 100 rows of progress; rows without student number or email in that window could be imported twice on resume. Audit metadata for imports holds counts only. | Reuses every records rule; bounded chunks per brain §3.4 |
| D-134 | 2026-10-22 | Uploaded rows are discarded when an import completes or is cancelled, except rows that need attention (kept for the error report). A scheduled purge of abandoned uploads is still to be built with the worker. | Data minimisation |
| D-135 | 2026-10-22 | `students.import` stays an admin/owner capability (staff can be granted it per membership); staff keep manual add/edit. | D-136 | 2026-10-22 | Go tests run with `-p 1` (CI and `make test`): the Postgres-backed packages share one test database and truncate it. | Prevent cross-package interference |
| D-137 | 2026-10-23 | `institute_invitations` is a GLOBAL (non-RLS) table: accepting happens before the invitee has any tenant context. Safety comes from the token hash lookup, the email match, and the store never exposing it through tenant routes (listing is filtered by institute id in SQL and the contract test checks isolation). Listed in `globalTables` with this reason. | RLS cannot express "the invitee may read exactly the row their token hashes to" without a tenant |
| D-138 | 2026-10-23 | Staff are invited by a one-time link the owner hands over (`/accept-invite#token=...`); no email is sent until the notification worker exists (M5). | D-139 | 2026-10-23 | Accepting requires the signed-in account's email to equal the invited email (case-insensitive) and the institute to be active. Every failure is one identical 404 (`ErrInvalidInvitation`); a wrong account does not burn the token. Rate limited 10/15 min per user and 30/15 min per IP. | No oracle for guessing tokens or emails; a forwarded link is useless to others |
| D-140 | 2026-10-23 | Only owners manage staff (`staff.manage`). Invitable roles are admin and staff, never owner; admins cannot carry grants; staff grants limited to the validated list. A removed member who accepts a new invitation is reactivated. Removal is soft. | Prevent privilege escalation and lock-out |
| D-141 | 2026-10-24 | A certificate template is a PRESET (classic, modern, minimal) plus fixed fields (orientation, accent colour, title, text with a closed list of `{{placeholders}}`, signatory, footer, show/hide switches). | D-142 | 2026-10-24 | Template versions are ALWAYS immutable (not only after first use): editing saves a new version, the database allows only INSERT/SELECT on versions (runtime role) and a trigger blocks UPDATE/DELETE even for the owner. | D-147 | 2026-10-26 | Certificate states: pending -> issued or failed, issued -> revoked. | D-148 | 2026-10-26 | Certificate numbers are `CERT-YYYY-NNNNNN`, counted per institute and UTC calendar year with a row-locked counter in the issuing transaction. | Brain default scope (unique per institute); the format was my default, say if you want another |

| D-151 | 2026-10-26 | Any member with `certificates.read` can download an institute's issued PDFs, also while the institute is suspended (a single download is not an export in the D-114 sense). | D-152 | 2026-10-27 | A bulk job issues ONE template version (pinned at creation) to every eligible enrollment of ONE batch, at most 500 per job. | D-153 | 2026-10-27 | Items run one at a time through the normal single-issue path. Duplicates are impossible because the one-live-certificate-per-enrollment index (0011) still applies; a job never has its own numbering or PDF code. | One code path for rendering, numbering and storage |
| D-154 | 2026-10-27 | At most one job per institute is queued or processing (partial unique index). Retry-failed also needs the slot. | Double clicks and second tabs cannot overlap; bounds Chromium load per tenant |
| D-155 | 2026-10-27 | Jobs run in the API process (no separate worker yet). A runner owns a job through a random token and a 2-minute lease renewed per item. After a crash or restart the job stays `processing`; `POST /bulk-jobs/{id}/resume` takes it over once the lease has expired, requeues a half-done item and continues. A runner holding an old token is refused. Shutdown (SIGTERM) stops runners between items and waits up to 15 s. A real worker (brain §6) can replace the in-process runner later without changing the store or API. | Smallest correct design; resumability proven by tests |
| D-156 | 2026-10-27 | If a runner died after storing a certificate but before recording the item, the next attempt adopts that certificate only when it is issued, from this job's creator, for the same template version and created after the job was created; any other existing certificate makes the item fail ("already has a certificate"). | No duplicate and no false credit |
| D-157 | 2026-10-27 | A failed item keeps a short fixed reason (no renderer output, no personal data). | D-165 | 2026-10-29 | Email delivery is independent of issuing: a delivery never changes the certificate, a failed delivery never rolls anything back, and a certificate can be (re)sent (at most 10 deliveries per certificate; one in progress at a time, enforced by a unique index). | D-168 | 2026-10-29 | Retries: 5 attempts per round; transient failures (network, timeout, 4xx) wait 30 s, 2 min, 10 min, 1 h; permanent failures (5xx, rejected recipient, authentication, TLS misconfiguration) fail at once.
